# RNG: автономная production-policy

> Текущий локальный кандидат включает [исправление медленного NV commit](rng-autonomous-v1-slow-commit.ru.md):
> ожидание RNG до 30 секунд, остановка после результата сохранения, совместимость установщика со schema 3.

[English](rng-autonomous-v1.md) · [Аппаратный план](rng-autonomous-v1-hardware.ru.md)

Локальный кандидат v2026.02.01, идентификатор политики `production-autonomous-v1`,
schema 3. Заменяет сервисную модель production-v1 только через явную миграцию.
Trial автоматически не повышается. Обычный запуск не требует PC, service-arm,
новой внешней случайности или 24-часовой изоляции. Устройства не изменялись.

## Сохранение и восстановление

192-байтовая запись `4VRSNV03` содержит поколение, накопленный счётчик закреплений,
привязку MAC/UUID, следующий seed, тег политики и SHA-256 для обнаружения повреждения.
`witness` содержит точную копию записи следующего поколения. Это секретный файл,
как `state`; его нельзя включать в отчёты, архивы или диагностические выгрузки.

Под исключительной блокировкой владельца каждое закрепление выполняется так:

1. Проверить текущие `state` и `witness`, отсутствие `pending`, `witness-next`
   и старого `attempt`. При противоречии не писать.
2. Создать `witness-next` с новым поколением, записать 192 байта, fsync файла,
   закрыть; переименовать в `witness`, fsync каталога.
3. Создать `pending`, записать ту же запись, fsync файла, закрыть;
   переименовать в `state`, fsync каталога.
4. Только после успешного завершения разрешить RNG в RAM. Сохранённый seed
   является преемником для следующего запуска, а не повторно используемым
   снимком уже выдававшего данные DRBG.

Свидетельство сохраняется после commit и не удаляется при завершении процесса.
Следующая транзакция заменяет его новым свидетельством. Поэтому выключение
питания во время нормальной работы после commit не оставляет маркер аварии.

| Наблюдаемое состояние без живого владельца | Действие |
|---|---|
| `state == witness`, обе записи корректны, временных файлов нет | Автономно закрепить следующее поколение до выдачи |
| Остался `witness-next` или `pending`, свидетельство отсутствует/отличается, старый `attempt` | `service-required`, без выдачи и автоматической повторной записи |
| Повреждён `state` или неверна привязка/метаданные | `invalid-state`, без отката на другую копию |
| Есть другой владелец | Второй broker отказывает `owner-busy`, первый продолжает работу |

Ошибка любой операции прекращает выдачу в текущем процессе. Gateway закрывает Web
и блокирует автоматические перезапуски отказавшего broker, сохраняя основной Gateway
и порты. Последующий управляемый запуск сначала читает состояние. Если потерянное
подтверждение оставило точное совпадение закреплённого преемника и свидетельства,
неоднозначность разрешена: используется новое поколение, спорная запись не повторяется.
При несовпадении даже многократные рестарты не выполняют новых записей состояния.

Локальные crash-тесты моделируют остановку процесса. Они не доказывают долговечность
CF после физического снятия питания: нужны испытания ядра 2.6.10, ext3, контроллера
и конкретной карты. Не предполагается, что карта честно выполняет fsync без проверки.
Возврат целого старого образа CF с согласованными записями не обнаруживается этим
протоколом; для защиты от такого отката нужна внешняя аппаратная опора. Старые образы
RNG не восстанавливать. Контрольная сумма не является защитой от администратора,
который может переписать обе записи и привязку.

## Эксплуатация и сервис

`4vrs-rng status /var/hda/4vrs-rng` читает с O_NOATIME, не создаёт lock-файл,
не удаляет остатки и не синхронизирует CF. Восемь — диагностический порог
`observation-threshold=8`, `threshold-reached=yes/no`; он не блокирует Web,
не является скользящей квотой и не доказывает ресурс CF. RTC/NTP не возвращают
счётчик. При переполнении 32-битного счётчика/поколения — сервисный отказ.

Для первичной активации либо миграции чистой schema 1/2:
`production-enable PATH --fresh-entropy-confirmed`. Для неоднозначного или
повреждённого состояния: отдельная операция
`service-recover PATH --fresh-entropy-confirmed`. Обе принимают ровно 32 свежих
случайных байта через stdin от доверенного внешнего CSPRNG, без вывода seed.
Не передавать seed аргументом, не сохранять его в shell history или журнале.
В production-сборке PATH находится на проверенной CF `/var/hda/`.

Перед сервисом остановить потребителей RNG в рамках отдельно разрешённых работ,
проверить носитель и обеспечить конфиденциальный канал. При валидном состоянии
смешивается старый преемник со свежей случайностью, поколение увеличивается.
Recovery также пропускает более новые корректные зарезервированные поколения
из свидетельств/временных записей. Если достоверных поколений не осталось,
создаётся новая последовательность со свежей случайностью; это не восстановление
старого RNG. При компрометации отдельно отозвать затронутые секреты/сессии.
24 часа ожидания не нужны. Старые `service-arm`, `service-resume` и флаг изоляции
новый CLI отвергает, чтобы не менять их прежний смысл молча.

Миграция с `attempt`/`pending` запрещена обычной командой enable: требуется
явный recovery. Миграция отзывает прежнюю policy до изменения seed; старый binary
не понимает schema 3 и отказывает без записи. Откат приложения нельзя совмещать
с восстановлением старого seed/образа CF.

Мастер CF проверяет schema 1/2/3; для schema 3 требует совпадения свидетельства.
Новый носитель мастер по-прежнему готовит в schema 1 без включённой политики:
после установки требуется **однократная явная активация** указанной командой.
Это первоначальная подготовка, не обслуживание каждого запуска. Обновление
пакета само по себе не переписывает RNG существующей CF.

## Частота записей и остающиеся ограничения

Один успешный commit — две записи файлов по 192 байта, два fsync файлов,
два rename и два fsync каталога. Создание lock-файла при первом запуске,
первичная подготовка, миграция и сервис добавляют операции. Чистое завершение
не пишет состояние. Проверка статуса не пишет. Это логические операции,
не число физических программирований NAND и не гарантия срока службы.

Для `R` принятых broker-запросов за один запуск ориентир успешных закреплений —
`max(1, ceil(R/1024))`; подготовка считается отдельно. Максимум 1024 байта на
запрос, минимум 60 секунд между ротациями сохраняются. Слишком ранняя ротация
закрывает Web: это отдельное ограничение нагрузки, не квота восьми поколений.
Одно спокойное включение в сутки: минимум 365 commit/год, 730 записей содержимого.
24 включения/сутки: минимум 8760 commit/год, 17520 записей содержимого.
10 000 broker-запросов за непрерывный запуск: около 10 commit.

Сбой посреди транзакции оставляет не более двух начатых записей содержимого;
дальнейшие неоднозначные старты не добавляют записей состояния. Но повторные
сбои **после завершённого commit** позволяют новые автономные старты и новые
commit: жёсткого предела износа или защиты от бесконечного внешнего reboot-loop
нет. Gateway не создаёт внутреннего цикла повторной записи после отказа.
Оценить реальные включения, ротации, блочный I/O, журнал ext3 и CF на аппаратных
испытаниях; не делать запись диагностики на каждый GET или status.

Web-нагрузка, запросы RNG и отдельный процесс проверки пароля измеряются раздельно.
HTTP/HTTPS, авторизация и согласованные задержки подключения не изменялись.
Два HTTP-выброса остаются наблюдениями с неустановленной причиной.
