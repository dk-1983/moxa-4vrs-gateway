# Повторная установка: no-op и repair

**Готово к выпуску в указанной ограниченной области; обязательные критерии закрыты.** Исторически подтверждён отказ platform verify при равном плане; диагностический опыт дал network-service-health, здоровый повтор — result3/no-op с сохранением PID Gateway/RNG и поколения. Неизменность PID Web не доказана. [Аппаратные результаты](release-final-noop-hardware.ru.md). Первопричина прежнего сетевого состояния не установлена и не объявляется установленной.

[English](release-final-noop.md) · [Матрица выпуска](release-final.ru.md)

Подтверждён FAIL аппаратного критерия: после повторного запуска того же установщика из `gateway-92e35241d9ee8d3f` итог result0 verify-installed, но Gateway/RNG/Web сменили PID, generation3→4 и TCP P1/P2 переподключились. Неизменный gateway.conf не доказывает равенство всего управляемого набора. Первоначальное ожидание harness только 3 секунды было ошибкой наблюдения асинхронной операции: блокировка отклонила попытку рестарта, Gateway оставался жив. Ожидание исправлено на конечный result, установку не повторяли. Смена PID/поколения подтверждена независимо от этого.

## Условия в коде

`install_orchestrator.c` сравнивает каждый элемент плана по kind, mode, size и всем байтам. В план входят не только ELF и gateway.conf, но также interfaces/resolver, confirmed/good, vendor/managed скрипты, clock-маркер, startup gates и ссылки. Для полного равенства дополнительно вызывается platform verify. Проверка target требует правильного Apache-состояния, идентичности/готовности Gateway, поддерживаемого наблюдения сети, settled/ready/error=0 владельца сети, DHCP lease и соответствия baseline адресов/масок/broadcast/up/default route/DNS по применимым правилам.

Только при полном равенстве и здоровой платформе получается result3 already-installed без stop/start. Отдельное отличие recovery executable исправляется без перезапуска служб. Поэтому result0 **verify-installed** со сменой PID означает транзакционный repair: либо различались элементы плана, либо platform verify отказал. Старый result не сохранял ветвь, но последующее чтение соответствующего журнала установило равный план и отказ platform verify. Более узкая историческая причина не доказана.

## Метод чтения журнала (выполнен в аппаратном опыте)

Новый установщик содержит отдельный **только читающий** режим. После согласованного размещения проверенного нового установщика на Moxa #2, из каталога пакета выполнить именно команды с аргументами:

```sh
./4vrs-install --decision-journal
./4vrs-install --status
cat /etc/4vrs-installer/active
```

Не запускать `./4vrs-install` без аргументов ради диагностики: это новая установка и может заменить нужный журнал. Диагностика читает два сохранённых slot-журнала под неблокирующей shared-блокировкой существующего install.lock. Не создаёт файлы, не выполняет recover, не читает CF/RNG и не меняет процессы. Проверяет контрольную сумму и allowlist путей штатным декодером. Выводит только путь и before/after kind/mode/size/content_changed; содержимое файлов и их хеши не выводятся. Занятый lock или повреждение дают ненулевой результат.

Соотнести slot с active и предыдущим result. Если журнал нужной повторной операции содержит отличие, назвать точный путь и метаданные; отличие содержимого разбирать локально по соответствующему генератору без экспорта секретов. Если все элементы равны, подтверждена ветвь platform verify, но конкретная историческая причина без дополнительных данных остаётся неизвестной. Если журнал уже заменён, не выдавать новый журнал за старый.

## Диагностика решения

Новый итоговый result сохраняет `decision`, `decision_health`, `decision_count`, `decision_path`, `decision_mask`. Маска первого отличия: 1 kind, 2 mode, 4 size, 8 различие байтов при одинаковом размере. Значения decision: no-op, repair-plan-differs, repair-platform-unhealthy, repair-recovery-only. Для plan-differs health не запускается, как прежде. Для platform-unhealthy сохраняется конкретный код: application-identity/readiness/absent, apache-inspection/running-state, network-observation/service-health, dhcp-lease, lan1/lan2-baseline, default-lan/gateway/dns-baseline. Финальный успешный verify не затирает исходную причину.

Проверки здоровья не ослаблены. Добавлены local normal/UBSan случаи равного здорового набора, отсутствующего управляемого clock-маркера и равного нездорового набора; отдельно проверены чтение journal без содержимого, занятая блокировка и повреждённая подпись. В результате будущего целевого опыта ждать конечный result, а не 3 секунды; result100 означает работу, не успех и не разрешение нового запуска.
