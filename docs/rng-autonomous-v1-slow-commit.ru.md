# Медленный NV commit: причина и исправление

[English](rng-autonomous-v1-slow-commit.md) · [Восстановление Moxa #2](rng-autonomous-v1-moxa2-recovery.ru.md)

Гипотеза подтверждена **локально на прежнем автономном кандидате** в реальной
цепочке Gateway → RNG client → broker. Содержимое CF Moxa #2 не читалось:
приписывать её текущий service-required этой причине без аппаратных данных нельзя.

## Воспроизведение

Host-only LD_PRELOAD fixture задерживает вызов fsync на 4500 мс после записи
`pending` либо `witness-next`. Это модель задержки, а не физическое испытание CF.
Используются настоящие Gateway/client/broker, публичный одноразовый seed и восемь
подменённых UART-транспортов. Probe сообщает только монотонное время, PID, сигнал,
код завершения и наличие обработчика/блокировки SIGTERM; ни одного байта RNG.

| Прежний кандидат | Задержка | Завершение broker от начала задержки | Результат |
|---|---:|---:|---|
| normal, pending | 4500 мс | 2996 мс | SIGTERM, signal 15; service-required |
| normal, witness-next | 4500 мс | 3006 мс | SIGTERM, signal 15; service-required |
| UBSan, pending | 4500 мс | 2994 мс | SIGTERM, signal 15; service-required |
| UBSan, witness-next | 4500 мс | 2999 мс | SIGTERM, signal 15; service-required |

Причинная цепочка проверяется утверждениями теста:

1. `rng_client_step()` отправляет запрос и через 3000 мс без ответа закрывает канал.
2. `web_gateway_step()` вызывает `rng_stop()`, который посылает SIGTERM.
3. Старый `rng_main` устанавливает обработчики **после** `rng_nv_start()`.
   Внутри задержанного fsync SIGTERM имеет действие по умолчанию и не заблокирован.
4. `waitpid` в Gateway подтверждает завершение именно по сигналу 15 до окончания
   задержки. RNG не выдавался. Осталась незавершённая транзакция, status возвращает 8.

## Исправление

- Ожидание первого байта ответа RNG после полной отправки запроса — до **30 секунд**.
  Отправка неполного запроса, получение начавшегося ответа и команда attach остаются
  ограничены **3 секундами**. Проверены точные границы 29999/30000 мс и трёхсекундная
  граница частичного ответа. Это ограниченное ожидание, не отключение тайм-аутов.
- Gateway блокирует SIGTERM/SIGINT вокруг fork/exec; broker устанавливает обработчики
  до NV I/O и только затем разблокирует сигналы. Остановка, пришедшая до main,
  обрабатывается без начала новой записи.
- На протяжении persist оба сигнала заблокированы: они не могут вызвать EINTR
  посреди fsync/write. После завершения либо отказа транзакции маска восстанавливается.
  Обработчик только запоминает запрос остановки; реальные ошибки I/O не повторяются.
- Перед выдачей после ротации проверяется остановка. Если она запрошена во время
  commit, broker завершает сохранение и выходит без выдачи RNG.
- При тайм-ауте Gateway сразу фиксирует отказ, закрывает Web и не создаёт цикл
  сигналов/повторных запусков. Основной Gateway и порты продолжают обслуживаться.
- Сервисный 30-секундный alarm ограничивает получение внешней случайности, но
  отключается перед сервисным сохранением; commit не обрывается этим alarm.

Проверки normal/UBSan: при 4500 мс Web запускается после commit; явный SIGTERM
во время commit приводит к согласованному состоянию без выдачи; при 32000 мс клиент
отказывает по своему пределу, но broker завершает commit примерно через 32004 мс
и status остаётся ready. Отдельно проверены сигнал до main и сигнал во время
ротации: 1024 прежних запроса обслужены, новое поколение закреплено, 1025-й ответ
после запроса остановки не выдаётся.

Порядок «надёжное сохранение → RNG» не изменён. SIGKILL, реальное отключение питания,
неисправная CF и бесконечно зависший I/O этим не устраняются. При зависшем fsync
broker может оставаться живым после клиентского отказа; автоматического SIGKILL
или повторной записи нет. Полная остановка Gateway может ждать такой процесс;
нужен отдельный аппаратный разбор, а не автоматическое прерывание commit.

Дополнительно исправлен установщик: статическая проверка принимает корректные
160-байтовую schema 1 и 192-байтовые schema 2/3. Установка и откат приложения
не включают RNG-файлы в свой план и не удаляют незавершённую транзакцию.
Повреждённое состояние по-прежнему отклоняется до остановки процессов.

## Повторение локальной проверки

В существующем контейнере `moxa-dev-20260909-064851`:

```text
python3 /workspace/source-host/tools/reproduce-rng-slow-commit.py baseline host
python3 /workspace/source-host/tools/reproduce-rng-slow-commit.py baseline ubsan
python3 /workspace/source-host/tools/qualify-rng-slow-commit.py build host ubsan target
python3 /workspace/source-host/tools/reproduce-rng-slow-commit.py fixed host
python3 /workspace/source-host/tools/reproduce-rng-slow-commit.py fixed ubsan
python3 /workspace/source-host/tools/reproduce-rng-slow-commit.py rotation host
python3 /workspace/source-host/tools/reproduce-rng-slow-commit.py rotation ubsan
python3 /workspace/source-host/tools/qualify-rng-slow-commit.py tests
```

Результаты baseline привязаны к сохранённым прежним бинарникам, а не к намеренно
испорченной новой сборке. Probe и управление задержкой отсутствуют в target ELF.
В комплект экспортируются только JSON с результатами; не временные состояния/логи.
Изменение ожидания не добавляет записей CF: частота успешных commit прежняя,
но исчезает воспроизведённое искусственное прерывание на трёхсекундной границе.
Два исторических HTTP-выброса по-прежнему имеют неустановленную причину: этот тест
не доказывает их связь с RNG и не смешивает Web-нагрузку с проверкой пароля.
