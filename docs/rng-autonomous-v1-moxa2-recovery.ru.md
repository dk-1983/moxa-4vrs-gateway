# Moxa #2: порядок восстановления service-required

[English](rng-autonomous-v1-moxa2-recovery.md) · [Причина локального сбоя и исправление](rng-autonomous-v1-slow-commit.ru.md)

**Это план, не выполненная операция.** Moxa #2 — только `192.0.2.15:22`.
Moxa #1 (`192.0.2.13:622`) не использовать. В этой работе устройство не читалось,
не изменялось; маркеры на нём не удалялись. Установка, остановка процессов,
reboot, извлечение CF и сервисная запись требуют отдельного разрешения.

## 1. Сначала зафиксировать состояние без записи

После разрешения на чтение проверить адрес/роль, mount `/var/hda`, PID и реальную
версию бинарников. Выполнить только `4vrs-rng status /var/hda/4vrs-rng` и сохранить
код выхода и несекретные строки. Для файлов state, witness, witness-next, pending,
attempt, owner.lock и production-policy собрать только наличие, размер, владельца,
режим и времена; не читать содержимое seed-файлов в терминал и не считать их хеши
для публичного отчёта. При живом broker допустимы State/SigCgt/SigBlk/SigPnd из
`/proc/PID/status`, длительность жизни и счётчики I/O. Не выгружать environ/cmdline,
core, TLS private key, cookies или конфигурацию с секретами.

Не удалять и не переименовывать pending/attempt/witness-next, не копировать их
поверх state, не восстанавливать старый образ CF. Не пробовать циклические запуски.
Если владелец ещё жив/в D-state, сначала разобраться с I/O; не делать SIGKILL для
ускорения обслуживания. Локальный тест объясняет возможную причину, но не доказывает
причину конкретного состояния этой карты.

## 2. Выбрать ветвь

| Результат проверки | Дальнейший порядок |
|---|---|
| ready, согласованная schema 3, владельца нет | Новая случайность не нужна. После установки исправления достаточно одного управляемого запуска Gateway для снятия его RAM-защёлки |
| service-required, корректный state, остатки/несовпадение свидетельства | Установить исправленный полный кандидат, не меняющий RNG-файлы; затем один explicit fresh recovery |
| invalid-state, неверные права/привязка, ошибки mount/CF | Не нормализовать права/UUID и не повторять запись вслепую. Сначала проверить носитель; обычный установщик повреждённый state отклоняет. Сервисный helper можно подготовить отдельно из проверенного пакета только по отдельному разрешению |
| CF неисправна или I/O зависает | Остановить процедуру. Подготовить замену носителя и новую последовательность RNG; не переносить старое RNG-состояние из образа |

Установщик исправлен для корректных schema 1/2/3. Его update/rollback не включают
каталог RNG в план записи, не очищают service-required и не повышают trial-policy.
Установка требует окна обслуживания: перезапуск приложения не обещает непрерывности
портов. Отказ одного RNG во время обычной работы не останавливает основной Gateway.

## 3. Подготовить свежую внешнюю случайность для аварийной ветви

Требуются ровно 32 байта от проверенного внешнего CSPRNG. Не передавать их через
старый SSH/console stack, аргументы команд, clipboard, отчёт или архив комплекта.
Сам запуск публичной команды по разрешённому каналу не требует передачи seed по нему.

Практический вариант без нового доверия к сетевому RNG прибора — физическая CF
в контролируемом Ubuntu PC, с отдельно разрешёнными штатным выключением/извлечением
и проверкой topology/mount. На исправной проверенной карте создать **отдельный**
закрытый каталог `/4vrs-service` (0700) и новый файл `fresh-rng-input` (0600,
O_EXCL/O_NOFOLLOW). Получить ровно 32 байта через `getrandom(GRND_NONBLOCK)`;
при EAGAIN/коротком результате прекратить операцию, без fallback и автоматического
повтора. Записать файл, проверить полный результат write, fsync файла и каталога,
закрыть; штатно размонтировать CF. Не трогать каталог `/4vrs-rng` и его маркеры.

Этот файл — секретный сервисный материал на том же доверенном носителе, не часть
установочного архива. Его нельзя включать в CF-образ для отчёта, пересылать или
повторно использовать. Предпочтительнее уже квалифицированный конфиденциальный
способ подачи stdin без временного файла, если такой способ имеется. Наличие
такого канала на Moxa #2 в этой работе не проверялось. Без безопасного источника
и доставки случайности recovery не выполнять.

## 4. Выполнить один сервисный переход после отдельного разрешения

После активации исправленных бинарников убедиться, что RNG не имеет живого
владельца и не будет запущен конкурирующим процессом. Использовать согласованное
окно обслуживания и управляемую остановку потребителей, а не удаление lock/маркеров.
Для варианта с подготовленным файлом команда на Moxa #2:

```sh
/var/hda/4vrs/bin/4vrs-rng service-recover /var/hda/4vrs-rng --fresh-entropy-confirmed < /var/hda/4vrs-service/fresh-rng-input
```

Это **будущая мутирующая команда**, здесь она не выполнялась. Только эта явная
операция может обработать незавершённые служебные файлы по протоколу: учесть верхнюю
границу корректных резервирований, смешать свежую случайность, закрепить новый
state/witness. Ручного rm/mv маркеров нет. При ненулевом результате не повторять
команду с тем же входом; сохранить файлы и перейти к разбору. 24 часа изоляции не нужны.

После успешного результата проверить status=ready, schema=3 и отсутствие живого
старого владельца; выполнить один управляемый запуск Gateway, проверить Web,
авторизацию и все рабочие порты. Не считать один лишь exit=0 восстановлением
всей системы. Новое поколение выше всех доступных корректных резервирований;
если достоверных записей не осталось, recovery создаёт новую последовательность,
не возвращает старый RNG. При компрометации отдельно отозвать затронутые секреты.

Сервисный вход после успеха должен быть выведен из использования в рамках
отдельно согласованной конфиденциальной уборки. Unlink на CF не гарантирует
физического стирания NAND; защита носителя остаётся частью модели. До разрешения
на сервис в этой задаче сохраняются и маркеры, и имеющиеся материалы.

## 5. Аппаратная проверка исправления

Замерить commit на реальной CF и Gateway readiness. Подтвердить, что задержка
более 3 секунд сама не вызывает обрыв сохранения; при превышении 30 секунд Web
отказывает, но нельзя принудительно убивать ещё сохраняющий broker. После
завершения — чтение status и управляемое возобновление, без слепых повторных записей.
Проверить перезапуск после завершённого commit и отдельно физическое питание;
host-delay тест этих испытаний не заменяет. Экспортировать только времена, коды,
поколения, сигналы и агрегированные показатели, без секретных файлов.
