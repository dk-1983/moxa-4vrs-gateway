# Автономный RNG: аппаратный план

[English](rng-autonomous-v1-hardware.md) · [Политика](rng-autonomous-v1.ru.md)

План ещё не выполнен. Любой доступ к устройствам, установка, reboot и управление
питанием требуют отдельного разрешения. Moxa #2 — строго 192.0.2.15:22; Moxa #1 —
192.0.2.13:622, не запасной адрес. Сейчас работа только локальная.

1. Зафиксировать SHA256 кандидата, модель/объём CF, ext3 и параметры монтирования,
   версию ядра и доступный способ наблюдения питания. Проверить пакет и ABI.
   Подготовить восстановление приложения, не копируя рабочие seed в отчёт.
2. На разрешённом тестовом носителе проверить мастер: начальная schema 1,
   однократная активация свежей внешней случайностью, совпадающие schema 3
   state/witness. Проверить update существующей schema 3 без изменения RNG;
   старый binary должен отказать без записи. Испытать миграцию schema 1 и 2,
   отдельно отказ миграции с остатками старой транзакции и explicit recovery.
3. Запустить основной Gateway и нагрузку всех восьми портов с измерением потерь,
   ошибок и задержек. Включить HTTP, отдельно HTTPS, авторизацию и процесс
   проверки пароля; не объединять эти нагрузки в одну причину задержек.
4. Выполнить не менее 20 штатных рестартов, включая восьмой/девятый, без PC-команд
   активации между ними. После каждого проверить рост поколения, готовность Web
   и неизменность Gateway. Проверить отдельный рестарт Web без перезапуска broker.
5. Снять питание во время обычной работы после подтверждённого commit, повторить
   не менее 20 раз. После ext3 recovery согласованное состояние должно запускаться
   самостоятельно; не требуются arm или 24 часа. Проверить отсутствие повторной
   выдачи на контролируемом тестовом интерфейсе; не журналировать реальные секреты.
6. На специально подготовленной инструментированной тестовой сборке перебрать
   точки до/после создания, записи, fsync, close и rename обоих файлов, а также
   fsync каталога. Затем повторить физические отключения на обычной сборке в
   выбранных временных окнах. Инструментированная сборка не входит в установочный
   пакет. Локальные NV_FAIL/NV_CRASH отсутствуют в target binary.
7. Для каждой точки определить итог чтением: совпадение обеих записей и отсутствие
   временных — безопасный следующий старт; иначе Web закрыт и обслуживание.
   При неоднозначности выполнить три рестарта и несколько status: отсутствие
   новых записей состояния, выдачи и повторов спорного поколения обязательно.
   Не удалять маркеры для прохождения теста. Проверить explicit fresh recovery.
8. Отдельно проверить короткую запись, ENOSPC/EIO, read-only CF, повреждение state,
   свидетельства, отсутствие CF и её потерю во время записи. Конкурентный broker
   не должен менять состояние первого. Повреждение выявляется без отката на
   старый слот. Восстановление из полного старого образа CF не поддерживается.
9. Перевести RTC назад/вперёд и включить NTP. Счётчик не уменьшается, восемь не
   закрывает Web. Проверить быстрый поток RNG: прежний минимум 60 секунд между
   ротациями остаётся отдельным ограничением.
10. Измерить число commit, файловых/блочных операций и задержек fsync при спокойной
    работе, реальной Web-нагрузке, отдельной проверке пароля и серии включений.
    Отдельные серии: сбой внутри транзакции (после отказа новых записей нет) и
    сбой после commit (каждый успешный рестарт добавляет commit). Не экстраполировать
    ресурс NAND только из двух записей по 192 байта.
11. Отдельная сетевая серия: обрыв/возврат LAN, смена доступности HTTP/HTTPS,
    повторная авторизация. Сравнить порты и задержки подключения. Два известных
    HTTP-выброса сохранять с неустановленной причиной до воспроизводимого объяснения.
12. Экспортировать только версии, коды ошибок, поколения/счётчики, времена,
    агрегированные показатели I/O и контрольные суммы публичных бинарников.
    Не экспортировать state, witness, staging-файлы, пароли, cookies, TLS private key
    или их секретные дампы. Повторно проверить состав отчёта и пакета.

**Препятствуют аппаратно квалифицированному автономному выпуску:** неиспытанная
долговечность CF при питании и ошибках записи, миграция/мастер на реальной CF,
реальная непрерывность UART/Modbus при отказах RNG, измерение обычной и аварийной
частоты записей. Сетевые сценарии — отдельная проверка Web/Gateway, также остаются
непроверенными на новом кандидате. Успешные host/UBSan тесты не закрывают эти пункты.
