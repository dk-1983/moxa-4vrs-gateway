# Аппаратная проверка web-ipc-v1 — Moxa #2

> Актуальная [матрица выпуска](release-final.ru.md). Серия сокращена пользователем до 10 и завершена 10/10. Критерий аппаратного no-op закрыт; готово к выпуску в области матрицы. Повтор серии питания не требуется.

[English](web-ipc-power-cycle-plan.md) · [Исправление и доказательства](web-ipc-lifecycle.ru.md)

Ниже сохранён исходный план для трассировки. Пользователь сократил обязательную серию до 10; 10/10 завершены. Это не требование повторить серию. Актуальные критерии — в матрице выпуска. Установка, доступ к устройству и каждое изменение питания требуют отдельного разрешения. Единственная цель — Moxa #2 **192.0.2.15:22**; Moxa #1 **192.0.2.13:622** не используется и не является запасным адресом. Обновление прошивки не требуется.

## Подготовка

1. Взять полный `4vrs-gateway-v2026.02.01-web-ipc-v1-candidate.tar.gz` из нового review-комплекта. Сверить SHA256 по приложенному `SHA256SUMS`; проверить `validation.json` и ABI. В мастере CF `gateway.tar.gz` должен быть байт-в-байт тем же архивом. Сохранить прежний rng-slow-commit-v1 с SHA256 `8e9fd95f2dd8392dea0adde301c69343a7a9443ccb2215714e7d0e5537a34978` и возможность обратимого обновления приложения. Не откатывать RNG state вместе с бинарниками.
2. После отдельного разрешения зафиксировать несекретные исходные сведения: адрес/порт, версии и хеши бинарников, PID Gateway/Web/RNG, режим Web, HTTP/HTTPS-порты, работу P1/P2, тип и права `/tmp`. Проверку RNG выполнять командой `status`, без чтения/выгрузки seed, state/witness, паролей или ключей. Согласованное ready-состояние не требует service recovery.
3. Обновить приложение штатным установщиком обратимым способом, сохранив основной шлюз `mbusd`, конфигурацию и RNG. Не удалять или переименовывать RNG-маркеры. Не трогать `/tmp/4vrs-web-945.sock.cycle02-preserved`. Для уже исправной CF не запускать новую RNG-активацию или переподготовку CF.
4. Проверить первый запуск: `/var/4vrs-web-ipc` — каталог 0711 с UID/GID Gateway; текущий `<PID>.sock` — socket 0666; `<PID>.lock` — обычный пустой файл 0600; точный socket-путь присутствует в `/proc/net/unix`. Проверить HTTP 200, выбранный HTTPS-режим, авторизацию и реальные P1/P2. Не записывать пароль/токен/cookie в отчёт. Снять baseline ошибок/счётчиков обмена.

## Исторический исходный план: 20 (согласовано и выполнено 10)

1. Для каждого номера 01–20 сначала записать PID, поколение и статус RNG, Web state/error, точный socket-путь, счётчики P1/P2 и время. Подтвердить завершённый startup commit по ready; не считать частично завершённый NV commit частью этой серии штатного восстановления.
2. Физически снять питание всего устройства без stop/reboot. Зафиксировать длительность отсутствия питания и вернуть его по согласованной процедуре стенда. Нельзя имитировать этот этап одним stop/start приложения.
3. С момента подачи питания измерять доступность Gateway, RNG ready и первый HTTP 200. Для этой серии выделить до 180 секунд наблюдения; записать фактическую задержку и число повторов, а не только PASS. Проверить наличие Web-процесса, соответствие socket текущему Gateway и записи в `/proc/net/unix`. Часы устройства могут меняться: длительность измерять монотонными часами стенда.
4. Проверить реальный обмен P1/P2/Modbus после каждого включения и сравнить ошибки с baseline. Записать несекретное поколение RNG: оно не должно откатываться; никакого обязательного service-arm при согласованном CF и никакой блокировки на восьмом поколении. Проверить выбранный HTTP/HTTPS и авторизацию отдельно от длительной GET-нагрузки/работы KDF.
5. PASS цикла означает автономные Gateway/RNG/Web и восстановленный обмен без ручного вмешательства. Любая интервенция, отсутствие Web, откат/неоднозначность RNG или потеря портов — FAIL. Сохранить тип/права/inode пути, точную строку `/proc/net/unix`, PID и статусы; не удалять файлы для получения PASS. После FAIL остановить серию для разбора. Предыдущие 20 stop/start и цикл 1 не засчитываются в новую серию; прежний цикл 2 остаётся FAIL, несмотря на HTTP 200 после переименования.

## Отдельные сценарии и критерии допуска

Для выпуска с заявлением об автономном восстановлении после питания препятствиями являются незавершённая серия выше и отсутствие целевого подтверждения поведения JFFS2/proc/прав. Дополнительно проверить на изолированном стенде повтор имени/PID с безопасно созданным осиротевшим socket нового пространства. Локальный тест уже покрывает этот случай; нельзя ради него подменять активный аппаратный endpoint или завершать Gateway без отдельного разрешения.

Отдельный блок квалификации RNG: питание внутри каждого этапа NV-транзакции, повреждение/недоступность/заполнение CF, неоднозначная запись и отсутствие автоматических повторов; реальные порты должны оставаться рабочими. Схема и ожидаемые исходы — [план RNG](rng-autonomous-v1-hardware.ru.md). Успешные 20 штатных power-cycle не доказывают эти сценарии или ресурс CF. До заявления о полном покрытии отказов питания/CF они остаются препятствиями.

Отдельный блок сети: обрыв/возврат линка, адресации и DNS при работающих портах и Web, длительная GET-нагрузка; два HTTP-выброса с неизвестной причиной сохраняются как наблюдения. Эти результаты не подменяют проверку пароля отдельным KDF-процессом. Измерить записи JFFS2/CF в обычной работе и при повторных отказах, не выводить физические NAND-записи из числа поколений.

При RNG service-required использовать [план восстановления RNG](rng-autonomous-v1-moxa2-recovery.ru.md) только после отдельного разбора и разрешения; IPC-остаток не является основанием для него. Содержимое RNG и внешнюю случайность в публичные отчёты не включать. Публикация релиза после серии требует отдельного решения.
