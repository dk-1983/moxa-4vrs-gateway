# Web IPC после потери питания — web-ipc-v1

> Актуальная [матрица выпуска](release-final.ru.md). Серия сокращена пользователем до 10 и завершена 10/10. Критерий аппаратного no-op закрыт; готово к выпуску в области матрицы. Повтор серии питания не требуется.

[English](web-ipc-lifecycle.md)

Кандидат v2026.02.01-web-ipc-v1 исправляет повторное использование имени UNIX socket после аварийного завершения. `/tmp` не считается RAM: на Moxa #2 это постоянная JFFS2. Исправление не меняет RNG, его маркеры, порядок фиксации seed, HTTP/HTTPS, авторизацию или отдельный процесс проверки пароля.

## Причина и аппаратные наблюдения

Для предыдущего rng-slow-commit-v1 (SHA256 установочного tar.gz `8e9fd95f2dd8392dea0adde301c69343a7a9443ccb2215714e7d0e5537a34978`) оператор сообщил: 20 stop/start и часовой GET прошли; физический цикл 1 прошёл; цикл 2 — **FAIL автономного запуска**. RNG ready generation31, Gateway/RNG и P1/P2 работали, Web отсутствовал. При повторном PID945 старый `/tmp/4vrs-web-945.sock` существовал без слушателя в `/proc/net/unix`. Прежний `bind` отказывал, Web получал error4 и повторял попытку через 60 секунд; очистка только при listener >= 0 пропускала частичный запуск.

После проверки типа, отсутствия destination и слушателя оператор переименовал только этот inode в `/tmp/4vrs-web-945.sock.cycle02-preserved`. Без перезапуска Gateway/RNG штатная повторная попытка дала HTTP 200 за **0,096739 с**. Это подтверждает связь отказа с IPC; ручное восстановление не превращает цикл 2 в PASS.

Источник этих аппаратных сведений — сообщение оператора. Указанные файлы `outputs/moxa2-rng-slow-commit-20260911/power-cycles`, включая `cycle-02-after-ipc-intervention.txt`, пока недоступны по известному локальному desktop-пути и в этой проверке независимо не прочитаны. Не приписываем им дополнительные PID, измерения или результаты. Два ранее отмеченных HTTP-выброса остаются отдельными наблюдениями с неустановленной причиной.

## Протокол владения

1. Gateway создаёт `/tmp/4vrs-web-ipc` с точным режимом 0711, своим UID/GID. Каждый предок проверяется через `lstat`: настоящий каталог, доверенный владелец; запись для других допустима только со sticky bit. Symlink, чужой владелец и неподходящие права вызывают отказ без исправления чужого объекта. Открытие каталога с O_DIRECTORY/O_NOFOLLOW и сравнение device/inode дополнительно проверяют идентичность.
2. Для `<PID>.sock` открывается `<PID>.lock`: обычный пустой файл 0600, один hard link, нужный UID/GID, без следования symlink. Неблокирующая `fcntl(F_SETLK)` удерживается до закрытия endpoint; дескрипторы имеют FD_CLOEXEC. Параллельный процесс не может отобрать endpoint.
3. Остаток можно удалить только если это socket нужного UID/GID с одним hard link, точного пути нет в успешно прочитанном `/proc/net/unix`, а повторная проверка device/inode совпала. Учитывается и bind без listen. Подключение к чужому сервису для проверки не выполняется. Ошибка чтения proc запрещает удаление. Обычный файл, каталог, symlink и активный socket остаются на месте.
4. После успешного bind сразу фиксируется идентичность inode, затем выполняются chmod 0666, listen и установка неблокирующего режима. Ошибка любого последующего этапа вызывает очистку своего inode под удерживаемой блокировкой, даже если listener ещё не был передан Gateway. Подменённый объект не удаляется и не получает chmod при очистке. Ошибка очистки оставляет остаток для следующей полной проверки; безусловного удаления нет.
5. Штатная остановка очищает только свой inode. Старое пространство `/tmp/4vrs-web-*.sock`, включая сохранённый аппаратный артефакт, новый код не трогает. Файлы `.lock` намеренно сохраняются: их удаление разрушило бы взаимное исключение между процессами, удерживающими старый inode.

Защита рассчитана на недоверенный Web и других непривилегированных пользователей; процессы с тем же доверенным UID/root могут менять каталог и не входят в эту границу. Web проходит через каталог 0711 к socket 0666, но не может менять его имя. Существующая проверка `SO_PEERCRED` по ожидаемому PID/UID сохранена. IPC-отказ оставляет Web недоступным с прежним error4/повтором; основной Gateway и порты продолжают работать. RNG-отказ по-прежнему отдельно закрывает Web и не допускает повторных NV-записей после неоднозначного результата.

Использованы API целевой Linux 2.6.10/libc: без openat, SOCK_CLOEXEC и предположения о tmpfs. ABI проверяется по сохранённым библиотекам XScale big-endian. Фактическое поведение JFFS2, proc и прав на целевом ядре требует аппаратной серии.

## Записи и ограничения

Полная регрессия дополнительно обнаружила гонку Disable/Enable: `rng_stop` закрывал каналы перед SIGTERM, broker мог увидеть EOF и выйти с кодом 22 до сигнала, а Gateway фиксировал error52. В Gateway теперь SIGTERM отправляется перед закрытием каналов. `test_rng_stop_order.c` вызывает настоящий `rng_stop` с моделируемым немедленным обработчиком EOF: прежний код воспроизводит ошибку в normal/UBSan, новый проходит. Это проверка порядка системных вызовов; аппаратный cycle 2 ею не переобъясняется. Код broker/client/NV не изменён, правило сохранения до выдачи и обработка неоднозначного commit сохранены.

Новый каталог создаётся один раз; для нового PID создаётся пустой lock, при повторении PID он используется снова. Успешный запуск создаёт socket и меняет его права; штатная остановка удаляет socket. После аварии остаток удаляется только при следующей безопасной проверке. Это метаданные постоянной `/tmp` на внутренней JFFS2, а не дополнительные записи RNG на CF. Физическое число записей flash из этих операций не выводится. Lock-файлы постепенно накапливаются по использованным PID; автоматической уборки wildcard нет. Проверка существующего чужого/активного endpoint не изменяет его, но новый lock может быть создан до отказа.

Политика [автономного RNG](rng-autonomous-v1.ru.md) и [исправление slow commit](rng-autonomous-v1-slow-commit.ru.md) сохранены: следующее состояние закрепляется до выдачи RNG; восемь поколений — диагностический порог, не предел износа CF. Неоднозначное сохранение требует отдельного восстановления RNG, а stale Web socket само по себе его не требует.

## Локальная проверка и оставшиеся препятствия

`test_web_ipc_endpoint.c`: 99 проверок в normal и UBSan — аварийный остаток/то же имя 945, конкурирующий процесс, активный и только bound socket, файл/symlink/каталог, чужой UID, ошибки после bind/chmod/listen/nonblock, ошибка cleanup/proc, подмена перед очисткой, небезопасный каталог.

`test_gateway_ipc_restart.py`: настоящие Gateway/Web/RNG, SIGKILL дерева тестовых процессов, оставшийся inode и то же имя при следующем запуске; HTTP 200, следующее поколение RNG и восемь моделируемых портов в normal/UBSan. Это не физический power-cycle и не проверка UART.

В том же тесте посторонний файл вызывает error4, остаётся неизменным, а Gateway продолжает цикл, RNG остаётся ready и восемь моделируемых портов активны. Целевые 4vrs-rng, 4vrs-web, 4vrs-kdf и 4vrs-install байт-в-байт совпадают с slow-commit-v1; изменился Gateway. На окончательном Gateway повторены slow commit 4,5/32 с и остановка при ротации в normal/UBSan.

Полный комплект содержит validation.json, ABI, перечень бинарников и SHA256SUMS. Согласованная аппаратная серия 10/10 завершена; её повтор не требуется. Закрытие критерия no-op и исключённые из заявлений сценарии питания внутри NV/ресурса CF/потерь Modbus перечислены в [актуальной матрице выпуска](release-final.ru.md). Исходный план сохранён для трассировки, устройства в текущей работе не изменяются.
